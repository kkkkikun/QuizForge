# QuizForge 长程规划（约 3.5–5 个月，课余节奏）

## 项目认识摘要

**QuizForge = 复习资料 → 刷题网页的转换工具**：`docx/pdf/txt → 摄取 → 规则解析+LLM兜底 → Quiz JSON → 单文件 HTML / React 多题库站点`。Python 侧工程化扎实（108 测试 + golden 快照 + CI），前端零测试、565 行单文件组件；解析规则与你自己的 3 份样本强耦合，已发现实际数据缺陷（CET 组题错误合并、重复题干透传、组题干截断 30 字）；工具不可分发（无 PyPI、无 Web 上传）。

**推广策略（你已确认）**：两阶段——① 中心化站点（同学发文档给你，你生成后挂 Pages 站）做出口碑，② 再把转换能力工具化。移动端优先，LLM 保持可选默认关。

## 总路线：6 个里程碑，每个都可独立交付、随时可停

```
M0 还债+质量关卡 → M1 移动端体验 → M2 运营化+反馈通道 → M3 解析泛化(持续) → M4 推广启动 → M5 工具化分发
     (1-2周)          (3-4周)          (2-3周)           (3-4周,可穿插)      (1周+持续)      (4-8周)
```

## M0：还债 + 数据质量关卡（一切推广的前提）

推广出去的内容不能有错。探索中发现的缺陷必须先修：

1. **修 CET 组题合并 bug**：`quizforge/patterns.py` 的 `CET_SUBCONTEXT_RE` 只匹配带数字的 `Conversation 1`，裸 `Conversation`/`Passage` 标题不更新上下文 → cet4 有 4 个 10+ 子题的巨型组。泛化正则让任意上下文标题行都重置分组，补 pytest 用例
2. **修组题干截断**：`parse.py` 中 `pending[0][:30]` 导致 "The tide of change: Embracing " 半句截断——组名改取上下文标题而非首段截断
3. **修前端白屏崩溃**：db 题库无填空题时，Dashboard 切"填空"tab 开练 → `questionsList[currentIndex]` undefined 崩溃（`PracticeSession.tsx`）
4. **修 `bg-slate-905` 无效类**（`PracticeSession.tsx:556`）、清死类型（`QuizSession`/`WrongQuestionItem`/`UserStats`）、tsconfig 开 `strict`
5. **★ 建立「生成物校验关卡」（本里程碑核心）**：新增 `quizforge/validate.py`，reactfmt/render 输出前自动校验 Quiz：题干重复（去重或告警）、选项数 <3、group 子题编号重复、匹配题答案序号越界/重复、空题干。CI 红灯门禁。这是推广期的质量守门员，永久生效
6. 顺手处理已登记技术债中高价值的 **重复题去重**（net 题库已有 2 组完全重复题干）

**验收**：`uv run pytest` 全绿 + `npm run lint/build` 通过 + 重新生成 data.ts 后校验关卡报出并修复上述已知数据问题。

## M1：移动端答题体验（3–4 周）

同学用手机刷题是核心场景，这是前端投入的大头：

1. **测试基建先行**：vitest + @testing-library/react + jsdom；先覆盖纯逻辑（`checkBlankAnswer` 容错判分、group 判分、localStorage 持久化、进度统计），再覆盖组件交互
2. **PracticeSession 拆分**：565 行单文件按题型拆成 `ChoiceQuestion`/`MultipleQuestion`/`BlankQuestion`/`GroupQuestion` 组件
3. **移动端优先重设计**：触控目标 ≥44px、题号网格与答题卡片的小屏布局、滑动切题手势、底部操作栏；桌面自动适配
4. **PWA 支持**：manifest + service worker 预缓存（纯静态站天然适合）——同学"添加到主屏幕"后离线可用、体验接近原生 App，是传播加分项
5. 接入 eslint（当前只有 tsc）

**验收**：手机浏览器实测（DevTools 移动仿真 + 真机）主流操作流畅；核心逻辑测试覆盖率达标；Lighthouse 移动端可用性 ≥90。

## M2：站点可运营化（2–3 周）

让别人用起来的"最后一公里"：

1. **★ 错题反馈通道（运营生命线）**：题目卡片加"报告问题"按钮 → 跳转预填内容的 GitHub Issue（题库 id + 题目 id + 题干摘要 + 用户备注），纯前端实现零后端。推广后必然发现错题，没有这个通道你就是瞎子
2. **错题本**：答错的题自动进错题集，Dashboard 可单独重刷错题——刷题工具的核心留存功能
3. **关于/使用说明页**：数据来源、隐私声明（所有进度只存本机 localStorage、不上传任何数据、LLM 仅在你本地生成阶段使用）、如何请求新题库
4. **题库生产流水线脚本化**：新 docx → `quizzes.yaml` 登记 → 生成 data.ts → 校验 → push，一条命令 ≤10 分钟，把"新增一个题库"的成本压到最低（推广期你会高频做这件事）
5. Issues 模板（题库纠错 / 新题库请求 / 功能建议）

**验收**：从收到同学文档到题库上线全流程走通一次；反馈按钮产出的 Issue 含足够定位信息。

## M3：解析泛化——去个人化（3–4 周，可与 M1/M2 穿插）

要吃下别人发来的任意文档，解析层必须摆脱"只认你自己的三份样本"：

1. **答案 key 区映射**（已登记技术债，最高价值）：答案统一列在文末的文档形态最常见，实现按题号映射回题目，让 NET 类文档免 LLM
2. **解析失败诊断**：识别 0 题/极少题时不再静默，输出人类可读诊断（识别到的结构样例 + 建议的文档格式），这是支撑"别人发文档给你"工作流的关键
3. **十五选十/选词填空**：等格式样本适配规则路径，或先走 `--llm-parse` 兜底路径支持
4. **模式积累机制**：每收到一份新文档 → 存入 `data/` 作回归样本 → 补 golden 快照 → 失败案例反哺 `patterns.py`。把"解析泛化"变成运营驱动的持续过程，而非一次性开发
5. 已登记低优先项酌情排：图片抽取（base64 内嵌）、阅读正文入 group 题面

**验收**：至少 3 份来自他人的陌生文档成功产出可用题库（校验关卡通过）。

## M4：推广启动（1 周准备 + 持续运营）

M0–M2 完成、M3 有初步泛化后启动：

1. 找 5–10 位同学试用：请他们发复习文档给你，全流程陪跑，收集体验反馈
2. README 分层重写：使用者视角（只需知道网址 + 如何请求题库）与贡献者视角分离
3. 站点加截图/预览图（README 里的占位一直空着）
4. 校内渠道传播（课程群等），观察反馈 Issue 数与新题库请求量作为推广指标
5. （可选）无后端访问计数（如 GoatCounter），评估要不要继续投入

## M5：工具化分发——第二曲线（4–8 周，依 M4 反馈决定启动时机）

把转换能力交到别人手里，**推荐浏览器端路线**：

1. **方案 A（推荐）：Web 上传界面 + 浏览器内转换**——Pyodide 打包 ingest/parse（纯规则，无 LLM），文档内容全程不上传，隐私是天然卖点；LLM 兜底改为用户自带 key（存 localStorage 直连 provider）或导出 JSON 回本地 CLI 补。工作量评估后再定 Pyodide 或渐进重写
2. **方案 B（并行小成本）：PyPI 发布** `quizforge` CLI（uv build），面向有 Python 环境的进阶用户，验证包分发体验
3. LLM 默认关、BYOK（你已确认的策略）；防滥用条款（仅处理教育用途文档）
4. 自建后端转换服务（FastAPI + 队列）明确不做——服务器成本与滥用问题在个人项目规模下不划算

**验收**：陌生人不上 GitHub、不装 Python，打开网页上传自己的 docx 就能拿到题库网页。
